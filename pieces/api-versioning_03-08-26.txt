Pinned to the Day You Signed Up

Every time Stripe ships a change to its API, millions of dollars of other people's businesses are running on the assumption that yesterday's request still works exactly the same way today. Payment forms that haven't been touched in three years. Invoicing systems built by developers who've since left the company. Subscription logic nobody remembers writing, quietly charging cards every month. All of it depends on a promise: that Stripe will not, without warning, change what happens when that code runs. And Stripe has never broken that promise, despite shipping changes to its API constantly — sometimes several times a month. The trick isn't caution. It isn't a slow, careful release cadence, or an army of engineers manually testing every integration before every deploy. It's a system, and the system is built on an idea that turns out to be far more interesting than it first appears: what, exactly, counts as breaking a promise?

That question is the real subject of API versioning. Most explanations of the topic jump straight to the mechanics — should you version in the URL, in a header, in a query parameter? — and treat it as a matter of taste, like choosing where to put a light switch. That's the boring part. The interesting part, the part that actually determines whether a company's API becomes something people trust enough to build a business on, is upstream of all that syntax. It's the judgment call about what a "breaking change" is in the first place. Get that judgment wrong and it doesn't matter whether you version in the URL or the header — you've already broken the promise. Get it right, and the syntax barely matters at all.

**The lease you signed on move-in day**

Here's a way to think about what an API version actually is. It isn't a number, or a label, or even really a snapshot of code. It's a lease.

When you sign a lease on an apartment, you're agreeing to a specific set of terms: this rent, these rules, this square footage, this parking spot. The building around you keeps existing in real time — the landlord can renovate the lobby, replace the boiler, repaint the hallways — but none of that touches your lease. The terms you agreed to on move-in day are the terms that apply to you, for as long as you keep renewing. A new tenant moving in next month might sign a completely different lease, with different terms, because the building itself has moved on. But you don't get pulled into that automatically. Nobody can hand you a new lease and call it the old one.

An API version is the same kind of promise. When a developer starts building against an API, they are — whether they realize it or not — signing a lease on a particular version of that API's behavior. They're trusting that the shape of the requests they send and the responses they get back will keep working the way it worked on day one, indefinitely, unless they explicitly choose to move to a new version. Break that, and you haven't shipped an update. You've let yourself into someone's apartment and rearranged the furniture while they were at work.

This is why the three "syntax" options for versioning an API — the ones that get treated as the whole topic — are really just three ways of implementing the same lease.

**URL versioning** puts the version number directly in the address, something like `api.example.com/v2/customers`. This is the most visible option: anyone reading a request can see exactly which version they're talking to, and moving to a new version means literally changing the address, the same way moving to a new apartment means a new address. It's clear and cache-friendly, but it multiplies your endpoints — every version lives at its own URL, forever, until you deliberately retire it.

**Header versioning** keeps the URL identical and instead specifies the version in a request header, something like `Accept: application/vnd.example.v2+json`. This is closer to a clause buried in the fine print of an otherwise identical-looking lease: the address never changes, but the terms attached to it can differ depending on what you specifically requested. It's tidier from the outside — one clean URL per resource — but it's less visible; you have to know to look for it, and it's harder to test casually in a browser.

**Query parameter versioning** adds the version as part of the URL's query string, like `api.example.com/customers?version=2`. It's the easiest to implement and the easiest to experiment with, but it's also the easiest to get inconsistent — a query parameter feels optional in a way a URL path segment or a required header doesn't, and it's the option most likely to get silently dropped somewhere in a chain of proxies and load balancers.

None of these is objectively correct, and companies you've heard of use all three. What they have in common is more important than what separates them: each one is a mechanism for saying "you get the terms you signed up for, not whatever terms are live today." The mechanism is a bikeshed. The promise underneath it is the whole game.

**What Stripe actually does**

Stripe's approach is worth studying because it takes the lease idea further than almost anyone else. Instead of version numbers — v1, v2, v3 — Stripe versions its API by release date: strings like `2023-10-16`. Every account is silently pinned, at the moment it's created, to whatever version was live that day. If you signed up for Stripe in 2019, your integration is still, by default, running against 2019's API behavior, even though Stripe's actual live codebase has moved on hundreds of times since. You can upgrade whenever you choose. Nobody forces you to.

The part that makes this genuinely elegant, rather than just generous, is what happens on Stripe's side of the wall. Their internal engineers only ever write code against the current version of the schema — the one live today. They are not maintaining a sprawling tangle of if-this-account-is-old, do-it-the-old-way branches scattered through the core codebase, which is what naive backward compatibility usually degenerates into over enough years. Instead, there's a compatibility layer that sits between the current codebase and the outside world, translating responses backward on the fly for any account still pinned to an older version. The landlord keeps a signed copy of every tenant's original lease on file. When a request comes in from a tenant on the 2019 lease, the system checks the file and answers accordingly — without needing to rebuild 2019's building inside 2024's building. The complexity lives in one well-defined translation layer, not smeared across the whole system.

This is what makes "millions of dollars of other people's businesses" not a figure of speech. There are real integrations, some of them years old, that have never once been touched by a Stripe API change, because they were never asked to move.

**So what actually counts as breaking the lease?**

This is where the topic gets genuinely interesting, because the honest answer is: it's blurrier than almost anyone assumes before they've been burned by it.

Take the most obvious case first, because it's illuminating precisely because it's counterintuitive. You'd think adding a new required field to an API response is always safe — you're not removing anything, not renaming anything, just adding more information. Surely that's additive, not breaking?

It depends entirely on one detail: does the new field have a default. If a client's existing code simply ignores fields it doesn't recognize — which is how most well-written API clients behave — then adding a field, required or not, changes nothing for them; they were never reading it, so they'll never notice it appeared. But if the field is required in the sense that clients are now expected to send it back, or if some part of the system starts validating its presence and rejecting requests that omit it, that's a different story: an old client that has no idea the field exists will start failing, silently or loudly, the very next time it makes a call. Give that field a sensible default and old clients that omit it simply get the default applied on their behalf; they never even learn the field exists. This is the whole insight in miniature: whether something counts as "breaking" hinges entirely on client-observable behavior, not on how big the change looks in a code diff. A one-line schema addition can be catastrophic. A sweeping internal rewrite can be invisible. The size of the change and the size of its blast radius are almost unrelated.

The second case is even less intuitive, and it's the one that catches experienced teams off guard: changing an error code. Imagine an API that, due to a bug, has been returning a 404 Not Found for a particular kind of request that should really return a 400 Bad Request. Somewhere out there, a developer noticed this months ago, and — reasonably, from their side of the fence — wrote code that says "if I get a 404 here, retry the request in five seconds, it's probably a timing issue." That code has been working fine. Then the API team, cleaning things up, fixes the bug and starts returning the correct 400. From the API's perspective, this is obviously a fix — arguably not even a change, just a correction of something that was always wrong. From the retrying client's perspective, it's a breaking change: the signal it was watching for has vanished, and its retry logic silently stops firing. Consumers write logic against observed behavior, not against a provider's intentions. They can't see your intentions. They can only see what actually came back last time, and they build on that, bugs and all. This is why "we're just fixing something that was broken" is one of the most dangerous sentences in API design — from outside, a fix and a change look identical, because both of them are just "the response is different now."

Semantic versioning — the familiar MAJOR.MINOR.PATCH numbering scheme most software uses — tries to formalize exactly this judgment call, and applying it to APIs is where its limits show most clearly. In theory, a MAJOR bump means "we broke something, expect to update your code"; a MINOR bump means "we added something, safe to ignore"; a PATCH means "we fixed a bug, nothing for you to do." In practice, as the required-field and error-code cases show, that clean taxonomy assumes the maintainer can always correctly predict what clients are watching for — and clients, especially at scale, watch for things maintainers never anticipated. Some clients parse error message strings. Some depend on the ordering of fields in a JSON object, even though ordering was never part of the contract. Some retry on specific status codes because of behavior they observed once, months ago, and never revisited. None of that is written down anywhere the API provider can see. The version number is a promise about intent. The lease is a promise about behavior. They're not always the same promise.

**Why the syntax question was never the point**

Once you see it this way, the appeal of Stripe's date-based, silently-pinned model makes more sense. It doesn't try to solve the "what counts as breaking" problem through better judgment alone — no amount of care eliminates the required-field trap or the error-code trap, because both depend on knowledge the provider structurally can't have: what every client, everywhere, happens to be watching for. Instead, the system is built so that even a wrong judgment call doesn't hurt anyone who didn't ask to be affected. If Stripe's engineers get a change wrong — misjudge something as additive that turns out to be observable — the compatibility layer still means nobody on an older pinned version feels it, because they were never moved onto the new behavior in the first place. The safety doesn't come from never making mistakes. It comes from making sure mistakes can only ever affect the version they were made in, never the leases that were already signed.

That's the real lesson underneath the versioning-strategy debate, and it's why the syntax question — URL, header, or query string — was always secondary. Any of the three can implement a genuine lease. All of them can also be implemented sloppily enough to break it, if the team behind them hasn't internalized the harder idea: that a promise to your users isn't measured by what you meant to change, but by what they can observe changing. An API is, in the end, just a very long-running conversation between systems that will never meet each other's engineers. Versioning is the discipline of remembering that whoever's on the other end of that conversation is still operating on the terms they agreed to when they first picked up the phone — and that it's your job to remember that, because they have no way of knowing you've since renovated the building.
