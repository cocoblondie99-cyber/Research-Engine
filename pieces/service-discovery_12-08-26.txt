Still Broadcasting

It was Christmas Eve, 2012, and a large fraction of the United States was doing the one thing you're supposed to do on Christmas Eve: sitting on the couch, half a mince pie in, queuing up something to watch. Netflix went dark. Not for everyone, and not for long in the grand scheme of outages, but for long enough that it made headlines the next day — "Netflix Down on Christmas Eve" is not a sentence a streaming company wants written about it, on the one evening of the year when everyone is watching television on purpose.

The cause, when Amazon Web Services published its post-mortem, turned out to be almost mundane: a problem in the load balancing layer of AWS's East region, where a maintenance process had accidentally deleted state data that the Elastic Load Balancers needed to know which servers were actually available to receive traffic. But "mundane" is doing a lot of work in that sentence, because the reason the failure cascaded the way it did — the reason a glitch in one piece of infrastructure could take down a service millions of people were actively using — is that the assumption underneath almost all networked software up to that point had quietly stopped being true. The assumption was this: a server lives at a fixed address, and if you write that address down somewhere, it will still be correct next week.

By 2012, at a company running its infrastructure on Amazon's cloud rather than its own hardware, that assumption was already fiction. Netflix's engineers had machines being created and destroyed by automated systems dozens of times a day, scaling up for the evening viewing peak and back down overnight, replaced when they failed a check, replaced again when a new version shipped. No server "lived" anywhere for very long. And yet a huge amount of the infrastructure they depended on — including, as it turned out, a piece of Amazon's own load balancing — still leaned on the old assumption somewhere in its plumbing: a list of addresses that was supposed to be current, and on that particular night, wasn't.

Netflix's response to the outage wasn't just to file a complaint with Amazon. It was to go build their own answer to a question that hadn't really needed asking in the era of fixed servers: when the map of "who is out there and reachable right now" can go stale in seconds, how do you keep a map that's actually true? The tool they built was called Eureka, and it belongs to a category of infrastructure now so foundational to how modern software runs that most engineers touch it every day without thinking about it twice: service discovery.

**The world where you just wrote the address down**

To understand why service discovery had to be invented, it helps to sit for a moment in the world before it was necessary — a world that, for most of the history of computing, was simply the way things were.

Say you're running a company's website in, roughly, the 1990s or 2000s. You have a web server. You have a database server. They need to talk to each other — the web server, when someone loads a page, has to ask the database for the customer's order history or the product catalog. How does the web server know where the database is? Someone writes it down. Literally: a configuration file on the web server contains a line that says, in effect, "the database lives at this IP address, on this port." That file gets read once when the application starts, and from then on, the web server just... remembers. It doesn't need to ask again, because the database isn't going anywhere. It's a physical machine, bolted into a rack, in a room someone has a key to. If it needs replacing, a human being does that deliberately, on a schedule, and updates the configuration file by hand at the same time.

This wasn't a hack or a workaround. It was a completely reasonable design for the infrastructure that existed. Servers were expensive, provisioned slowly, and treated — this is the phrase that stuck — like pets: given names, cared for individually, nursed back to health if something went wrong rather than casually replaced. In a world of pets, a written-down address is not a liability. It's just a fact, the same way you'd write down a friend's home address rather than ask for GPS coordinates every time you wanted to visit.

**Then the pets became cattle**

Cloud computing didn't break this model with a single dramatic event. It eroded it, gradually, as the economics of infrastructure flipped. Instead of buying a physical machine and keeping it running for years, companies started renting computing capacity by the hour, and then by the minute, from providers like Amazon. And once a server is something you can create in ninety seconds and destroy just as fast without touching a single wire, the entire logic of how you run infrastructure changes. Why keep ten machines running around the clock when you could keep three running at 3 a.m. and forty running during the dinnertime streaming rush, scaling automatically as demand rises and falls? Why nurse a struggling machine back to health when it's cheaper and faster to just kill it and spin up a fresh one?

The industry's own name for this shift was blunt: servers went from being pets to being cattle. You don't name a cow. You don't take an individual cow to the vet for something minor. If one gets sick, you replace it, because the herd is the unit that matters, not any single animal in it. Containers pushed the logic further still — where a cloud server ("virtual machine") might live for hours or days, a container, the lightweight packaging technology behind tools like Docker and Kubernetes, might live for seconds, spun up to handle one burst of work and torn down the moment it's done.

This is a genuinely strange environment to build software in, if you stop and picture it. At any given moment, the actual physical or virtual location of "the payments service" or "the recommendation engine" is not a fact anyone wrote down, because it changes too often for writing it down to mean anything. A configuration file with a fixed IP address in it isn't just inconvenient in this world — it's actively wrong within minutes of being deployed. And that's the exact assumption Amazon's load balancer leaned on the night things went sideways for Netflix: a map that was current when it was drawn, and stale by the time anyone needed to read it.

**A fleet, not a street plan**

Here's the picture that actually captures what service discovery does, and it isn't a phone book — a phone book implies something static enough to print and distribute once a year, which is precisely the thing this problem does not resemble. It's closer to a city's food truck scene tracked through a live app.

Imagine a fleet of food trucks scattered across a city on any given day. They don't have fixed addresses — a truck that was on Fifth and Main at noon might be three miles away by two, might have broken down and gone home for repairs by three, might have a brand new truck standing in exactly where the old one used to be by four. A printed street map with truck locations marked on it would be laughably wrong within the hour. Nobody would bother printing one.

Instead, there's an app. Each truck runs a little device that broadcasts a signal: I'm here, I'm open, I'm cooking. The app aggregates those signals into something that looks, at any given instant, like a map — but it isn't a map in the old sense, drawn once and trusted. It's a live feed, rebuilt continuously from whoever happens to be broadcasting right now. A truck that goes quiet — because it packed up, because its device died, because it drove off without telling anyone — simply stops appearing. Nobody has to manually remove it. Silence is enough to fall off the list.

That live feed, in the language of cloud infrastructure, is called a service registry, and the process of trucks announcing themselves and getting removed when they go quiet is what makes it a discovery system rather than a directory. The registry is the thing every hungry customer, or every hungry piece of software, consults instead of trusting a fixed address that was true only at the moment it was written.

And this is where the analogy earns its keep, because two very different kinds of hungry customer use that app, and cloud software actually has an equivalent split.

Some customers open the app themselves, see which trucks are currently near them and open, and walk over to one directly. They did the discovery themselves; the app just gave them current information to act on. This is what engineers call client-side discovery — it's the model Eureka, the tool Netflix built after that Christmas Eve outage, was designed around. In client-side discovery, the piece of software that needs to make a request — "I need the recommendations service" — queries the registry itself, gets back a short list of currently-healthy instances, and picks one to talk to directly. The upside is that there's one less hop in the middle, which matters at scale; the downside is that every single client needs to know how to speak to the registry and make a sensible choice, which pushes complexity out to the edges.

Other customers don't want to deal with any of that. They call a delivery service, describe what they're craving, and let a dispatcher figure out which truck is closest and available, then send a driver to fetch it. The customer never touches the live feed directly — the dispatcher does that on their behalf. This is server-side discovery: a router or load balancer sits in front of the registry, does the lookup, and forwards the request onward, so the client just needs to know one fixed address — the dispatcher's number — and can stay blissfully ignorant of everything moving around behind it.

Real systems, in practice, almost always use both at once, in different layers of the same architecture. Traffic coming in from the public internet, from a browser or a phone app that has no business knowing anything about a company's internal cluster layout, goes through server-side discovery — it hits a load balancer, which handles the lookup. But traffic moving between services inside that cluster — the recommendations service asking the user-profile service for data, dozens of times a second — often uses client-side discovery, because at that volume the extra hop of a router in the middle adds up, and the calling services are already sophisticated enough to talk to the registry directly.

**The part that actually does the work**

Here's the thing that's easy to miss if you stop at "there's a live registry instead of a static file," which is that the interesting engineering isn't the registry at all. It's what keeps the registry honest.

Go back to the food truck app for a second. The reason it's trustworthy isn't that it has a big database of trucks. A big database of trucks is exactly what a printed map is — it's just electronic. What makes it trustworthy is that it's constantly re-verifying: every truck's device is expected to keep broadcasting, and the app is designed to notice, fast, when one stops. That continuous re-checking is the entire value proposition. A registry that only removed trucks when someone manually told it to would be barely better than the printed map, just slower to go stale instead of instantly wrong.

In real infrastructure, this re-checking has a name — health checking — and it's genuinely the load-bearing idea in the whole system. Tools like Consul, one of the most widely used service registries, run continuous probes against every registered instance: sending an HTTP request and checking for a healthy response, opening a raw TCP connection just to see if anything answers, or waiting for the instance itself to send a heartbeat within an expected time window and assuming the worst if it goes quiet. Fail enough of those checks, and Consul doesn't wait for a human to notice — it pulls the instance from the list of things it will hand out as an answer to "who's available." The registry, in other words, behaves less like a directory and more like a hospital's patient board: being on the list at all is conditional, continuously, on currently being alive. It's not a record of who was here. It's a record of who's still here, re-earned every few seconds.

And this is where a distinction shows up that a lot of people building on this infrastructure never quite notice, because it's usually hidden a layer down: keeping a consistent, agreed-upon record and continuously verifying that the record is still true are actually two separate jobs, and different tools choose to do different amounts of each.

etcd, the key-value store that quietly forms the backbone of Kubernetes itself — every pod, every service, every configuration change in a Kubernetes cluster ultimately gets written to etcd — deliberately does not do health checking. It's built to solve a hard and narrow problem extremely well: keeping a single, consistent source of truth that many machines can read and write to at once without ever disagreeing with each other about what the current state is, even if some of those machines crash mid-write. That's a genuinely difficult distributed-systems problem, and etcd's entire design is bent toward solving it correctly. But etcd itself has no opinion about whether the service listed in it is actually alive right now. Something else — Kubernetes' own controllers, in that case — has to layer health checking on top.

Consul, by contrast, bundles both jobs into one tool: it stores the registry and it does the continuous health probing that keeps that registry current, out of the box. Neither approach is simply better — etcd's narrower focus is precisely why it can be trusted as the single source of truth for something as consequential as an entire Kubernetes cluster's state, while Consul's all-in-one design makes it faster to stand up service discovery without assembling the pieces yourself. But once you see the split, you can't unsee it: "service discovery" isn't one problem wearing one hat. It's a consistency problem — agreeing on the facts — bolted to a truthfulness problem — making sure the facts are still facts — and a tool's whole personality comes from how it chooses to handle, or not handle, each half.

**What changed, underneath**

It's worth sitting with how quietly all of this happened. Nobody woke up one day and decided static configuration was obsolete; it simply stopped matching the world underneath it, one ephemeral container and one autoscaling event at a time, until an entire new category of infrastructure had to be invented just to keep software able to find other software — a problem so basic, so pre-verbal in how computing works, that for decades it hadn't needed a name.

That's the quiet lesson sitting inside the food-truck app, and inside the outage that helped bring the modern version of it into being: the hard part of finding something was never really the map. It was staying honest about the fact that the map is only ever a description of a moment that has already passed — and building something that never stops checking, so the moment it's showing you is always the one you're actually standing in.
