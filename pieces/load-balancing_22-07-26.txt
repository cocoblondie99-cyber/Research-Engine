Any Server Will Do

Here's a question worth sitting with for a second: when you load a website that's serving millions of people at once, how does the system decide which of its thousands of identical machines actually answers you? Not "the internet" in some abstract sense — one specific server, somewhere in a data center, has to pick up your request in the next few milliseconds. Multiply that decision by every request from every user, all day, every day, and you have one of the quietest, least glamorous, most load-bearing (pun intended) problems in computing: load balancing.

It sounds almost too simple to be interesting. Spread the work around. Don't let one machine do everything while its neighbours sit idle. But the more you look at it, the more it turns out that load balancing is a problem with two very different personalities. For a huge swath of internet traffic, it actually is that simple — a solved problem, mechanical, almost boring. For another swath, it becomes one of the trickiest coordination puzzles in distributed systems, and the entire industry has spent decades building increasingly elaborate patches to work around a fact it can't undo. The dividing line between the easy version and the hard version is a single question: does the server need to remember you?

**The easy case: any server will do**

Start with the simple world. Imagine a service — say, a site that converts currency, or resizes images, or checks whether a piece of text contains spam. A request comes in, a server does some work, a response goes out. Crucially, the server doesn't need to know anything about you beyond what's in this one request. It has no memory of your last visit. It doesn't matter which of the thousand identical machines in the pool handles it, because they're all carrying an identical copy of the same code and the same (lack of) history. This is called a stateless service, and it is, from a load-balancing perspective, a gift. Any machine can serve any request equally well, which means the only real question is: which idle-ish machine should get this one?

There are a handful of standard answers, and each is intuitive enough to explain in a sentence.

Round robin is the simplest: requests are handed out in strict rotation — server one, then two, then three, then back to one — regardless of how busy each one currently is. It's the load-balancing equivalent of dealing cards: everyone gets a turn, evenly, no favourites. It works well when every request takes roughly the same amount of effort to fulfil.

Least connections looks instead at who's currently least busy, and sends the new request there. If server three is juggling four open connections and server one only has one, the request goes to server one. This is a better fit when requests vary wildly in cost — some take ten milliseconds, some take ten seconds — because blind rotation would happily send you to a server that's already drowning in slow work.

IP hash takes a different approach entirely: it runs the client's IP address through a mathematical formula (a hash function) that reliably produces the same output every time for the same input, and uses that output to pick a server. The effect is that the same client keeps landing on the same server, every time, without the load balancer having to remember anything — the address itself determines the destination, deterministically, on the fly.

Weighted variants layer on top of any of these: if server five is twice as powerful as the others, it gets weighted to receive twice the traffic. This is common in real infrastructure, where a data centre accumulates newer, beefier machines alongside older ones and wants to route accordingly rather than treating them as interchangeable.

All four of these strategies share one quiet assumption: it genuinely does not matter which server answers you. That assumption is doing enormous, invisible work. The moment it stops being true, the whole tidy picture falls apart.

**The moment memory enters the room**

Here's where it gets interesting. Suppose the service isn't stateless. Suppose it's an online shopping site, and you've just added three items to your cart. Or it's a chat application, and you have an open, live connection to a server for real-time messages. Or you've started uploading a large file, and the server currently holds the first sixty percent of it in memory. In each of these cases, one specific server now knows something about you that no other server knows. Your session — your cart, your live connection, your half-finished upload — lives, at least temporarily, on that one machine.

Suddenly "any server will do" becomes "only this server will do." If your next request gets routed to a different machine by round robin, that machine has never heard of you. Your cart is empty. Your chat connection doesn't exist. Your upload has vanished. The load balancer's job hasn't gotten harder in the sense of requiring more computation — it's gotten harder in the sense that it now has a wrong answer it can silently give, and the system has no way to notice.

This is the fork in the road that shapes almost everything else about load balancing in practice: stateless traffic is easy, and statefulness is the whole difficulty. Every real system that handles both is running a negotiation between the two, and the industry has built an entire toolkit of workarounds — not solutions, workarounds — to manage it.

The most common patch is called session affinity, or "sticky sessions." The idea is to force the same client back to the same server every time, usually by having the load balancer drop a cookie in the client's browser that records which server handled them first. On every subsequent request, the load balancer reads the cookie and routes accordingly. It's simple, and it works, right up until it doesn't: if that one server crashes, every user whose session was pinned to it loses their state entirely, with no graceful fallback, because the whole point of the sticky cookie was to avoid needing one. Stickiness also quietly undoes the benefit of load balancing in the first place — a server that happens to attract a disproportionate number of long-lived, chatty sessions ends up doing more work than its neighbours, and there's no easy way to rebalance without breaking the very sessions you were trying to protect.

The deeper, more honest fix is to stop keeping state on the server at all — to move the cart, the session data, the upload progress into a shared external store (a database, a cache like Redis) that every server can read from and write to equally. Do that, and the servers go back to being interchangeable; the statefulness hasn't disappeared, it's just been relocated somewhere that doesn't care which machine reaches it. This is why so much modern infrastructure advice boils down to "keep your services stateless" — it's not a stylistic preference, it's a direct attempt to stay on the easy side of the load-balancing fork for as long as possible. But it isn't free: an external store adds a network hop to every request, and now that store itself has to be fast, available, and consistent, which is its own hard problem.

**Fast and blind, or smart and slower**

There's a second major dividing line in load balancing, orthogonal to the statefulness question, and it comes down to which layer of the network the load balancer is willing to look at.

A Layer 4 load balancer works at the transport layer — it looks only at IP addresses and port numbers, the equivalent of reading the outside of an envelope without opening it. It doesn't know if the traffic inside is a webpage request, a video stream, or a game's real-time position updates; it just routes based on where the packets are addressed. This makes it extremely fast, because there's almost nothing to inspect, and it's the natural choice for things like online gaming or video streaming, where every millisecond of added delay is felt directly by the user.

A Layer 7 load balancer, by contrast, works at the application layer — it actually opens the envelope. It reads HTTP headers, cookies, and URLs, and can make genuinely intelligent, content-aware decisions: send requests for /images to one pool of servers and requests for /api to another, or read that sticky cookie and route accordingly. But this intelligence costs something concrete: to read the contents, the load balancer has to fully terminate the client's connection and open a brand-new one to the chosen backend server, effectively running two separate conversations instead of one continuous pass-through. That's real added latency, paid on every single request, in exchange for the ability to make a smarter choice.

So the two axes — stateless versus stateful, and fast-and-blind versus smart-and-slower — combine to describe most of the load balancing decisions an engineering team actually makes. A gaming platform wants Layer 4 and stateless, for raw speed. An e-commerce checkout wants Layer 7, because it needs to read cookies and route intelligently, and it's already dealing with statefulness anyway.

**The problem with reshuffling everything**

There's a subtler wrinkle even within the "any server will do" world, and it shows up the moment the pool of servers itself changes — when a machine is added, or one dies. Imagine you're using something like IP hash to route clients to servers, and you have ten servers in the pool. The hash function essentially treats those ten servers as ten slots and decides which slot each client falls into based on a calculation involving the total number of servers. Now add an eleventh server. The maths that decided where everyone went has changed — the calculation now divides by eleven instead of ten — and in a naive implementation, that single addition can reshuffle almost everyone's destination. Nearly every client gets rerouted to a different server than the one they were just talking to. For stateless traffic this is a minor inconvenience. For anything holding session state, cached data, or an open connection, it's a mass eviction event triggered by the completely ordinary act of adding one more machine to help with load.

Google ran headlong into this problem at a scale most companies never will, building Maglev, the software load balancer behind their own infrastructure, and their answer was a technique called consistent hashing. Instead of a hash table that treats "which server?" as one big calculation dependent on the total server count, consistent hashing subdivides the space of possible outcomes into a very large number of small buckets — think thousands of them — and assigns servers to buckets rather than clients directly to servers. When a server is added or removed, only the buckets it owned need to move to a neighbour; everyone else's assignment stays exactly where it was. The practical effect is that scaling a fleet up or down, or losing a machine to a crash mid-session, disturbs a small, predictable fraction of traffic instead of nearly all of it. It's the difference between renumbering every house on a street when one new house is built, versus just giving the new house the next available number and leaving everyone else's address alone.

**The restaurant host**

If all of this still feels abstract, picture a restaurant host standing at a podium during the dinner rush. Parties keep arriving in an unpredictable stream. Tables fill and empty at different rates depending on how quickly each group orders, eats, and pays. The host's entire job is to decide, in real time, who goes where — and getting it wrong has consequences: one server drowning under six tables while three other servers stand around with nothing to do.

Round robin is the host who seats parties in strict rotation, ignoring how full anyone's section currently is. Least connections is the host who glances around and sends the new party to whichever server's tables are closest to clearing. IP hash is the host who's decided, for whatever reason, that the Joneses always go to table four — every single time, no exceptions, no thought required.

And session affinity is what happens when the Joneses leave their coats draped over the chairs at table four and step out for some air. Now they can't just be seated anywhere convenient when they come back — they have to return to table four specifically, because that's where their coats are. The host's job, which was simple a moment ago, just got a permanent constraint attached to it, and it will stay attached until the Joneses leave for the night and someone finally clears the table.

That's the entire shape of the problem, scaled up to millions of requests per second: routing is easy until something is left behind at a specific table, and once that happens, the elegant simplicity of "seat them wherever" is gone for good — replaced by a web of exceptions, stickiness, and careful bookkeeping that exists for no reason other than the fact that somebody's coat is still on that chair.

**Why the patches, not a fix**

It's worth being honest about what all of this amounts to: none of it actually solves statefulness. Sticky sessions don't eliminate the risk of losing a session when a server dies, they just narrow the odds. Moving state into a shared external store doesn't remove the coordination problem, it relocates it to a system that now has to be fast and reliable enough to answer every request instantly. Consistent hashing doesn't stop reshuffling, it just minimises how much of it happens per change. Every technique here is a negotiation with a fact that can't be negotiated away — that once a server holds something about you, it has to keep holding it, or something has to move that knowledge somewhere the server can reach.

That's a strange thing to sit with, for a piece of infrastructure most people assume is fully solved. But it's also, in a way, reassuring. The reason load balancing still involves genuine engineering judgment — not just picking an algorithm off a shelf — is that the underlying tension it's managing is a real one, present in any system where multiple actors need to share limited resources fairly while some of those actors need to be remembered. Restaurants have the same tension. So does every human system built around finite attention and a stream of people who each, at some point, need someone to recognise them specifically. Load balancing just makes that tension visible in a place most of us never think to look: the machinery quietly deciding, thousands of times a second, who gets seen next.
